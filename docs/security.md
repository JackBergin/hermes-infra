# Security and threat model

## Scope

Hermes can execute tools and ingest untrusted content. Docker packaging makes dependencies reproducible; it is not itself a security boundary against a sufficiently privileged agent.

The deployment protects against accidental loss of a single server's application state **only if** backups are stored outside that server and regularly restored. It does not protect against compromised host root, stolen backup encryption keys, malicious upstream images, or deliberate deletion by an administrator with full access.

## Boundaries and protections

1. **Secrets**: The root Compose `.env` contains only deployment settings. Hermes credentials are generated by Hermes into the ignored `state/.env`. Any archive containing that state is sensitive. Do not print/archive-upload it to public CI artifacts or Git LFS. `make reset` keeps the previous state as a Git-ignored `state.old-<UTC time>/` folder that still holds those credentials; delete it once you no longer need it.
2. **Skills**: The reviewed Git-managed skills mount is read-only. Hermes native `skills.write_approval` is enabled by `make configure`. This is not a comprehensive defense against malicious skill code and it does not block local skills from shadowing external skills.
3. **Container**: Preserve the official s6 entrypoint for privilege drop and first-boot initialization. This stack does not expose `/var/run/docker.sock`, host credential directories, or gateway/API ports. The only published port is the login-protected dashboard on host loopback (see [Dashboard exposure](#dashboard-exposure)). It sets `no-new-privileges` but intentionally retains privileges needed by Hermes entrypoint initialization.
4. **Image**: Prefer a digest pin. Review Docker image provenance and Hermes upstream security announcements. Never accept untrusted image digests in automated upgrades.
5. **Backups**: The local ZIP is plaintext, stored mode 0600 under ignored `backups/`. Restic encrypts repository data with a password supplied through host environment/secret manager; protect the password and repository access separately.
6. **Restore**: An import overwrites matching Hermes files but may leave unrelated files in a non-empty target. Prefer a clean recovery host/state directory. Production restore is blocked on non-empty state by default.
7. **Permissions**: Hermes published images normally use container UID/GID 10000. The host bind mount may be inaccessible to the host login user, depending on filesystem ownership. Do not make sensitive state world-readable to work around this. Use documented UID/GID mapping when necessary.

## Dashboard exposure

**What it can do.** The Hermes web dashboard reads and writes `state/.env` (every provider key and token), edits configuration and sessions, and can run agent commands and shell hooks. Treat a dashboard login as equal to the agent's full credentials plus command execution.

**Exposure.** The dashboard is off (`HERMES_DASHBOARD=0`) until `make dashboard-auth` sets a login and enables it. Compose publishes container port 9119 on host `127.0.0.1` only, so it is not reachable from the LAN or the internet unless someone changes that binding or forwards the port.

**Controls.**

1. **Login always required.** Inside the container the dashboard binds `0.0.0.0`, which Docker port forwarding needs. That bind engages Hermes' fail-closed auth gate: without a login Hermes refuses to start the dashboard, and with one, every client must sign in, including local host processes and the agent's own tools inside the container.
2. **No plaintext password at rest.** `make dashboard-auth` reads the password with a no-echo prompt and stores only a scrypt hash in `state/.env`. The password never appears in process arguments, the Compose `.env`, or Git. The command also removes any plaintext `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD`, because Hermes would prefer it over the hash.
3. **Revocation.** Each run writes a new token-signing secret, which signs out every existing session. Rerun it to rotate the password or revoke a lost browser session.
4. **Upstream limits.** Hermes rate-limits password logins (10 per minute per client IP) and records login events in `state/logs/dashboard-auth.log`.

**Residual risks.**

- Any user or process on the host can reach the login page and guess passwords, subject to the rate limit. On a shared host that includes other local accounts.
- Traffic is plain HTTP. That is acceptable over loopback only.
- The hash and signing secret live in `state/.env`, so they are in every backup and readable by the agent. Whoever can read that file can forge a dashboard session, but they already hold every other credential in it, so this adds no new privilege.
- Signed-in browsers stay signed in for up to 30 days through refresh tokens. Sign out on shared machines and rerun `make dashboard-auth` to revoke.
- The gate is upstream code, hardened in June 2026 after exposed dashboards were abused. Keep the pinned image current with Hermes security releases.

**Remote access.** Do not rebind the dashboard to `0.0.0.0` or a LAN address; the username/password provider is not meant for direct network exposure. Use an SSH tunnel (`ssh -N -L 9119:127.0.0.1:9119 user@server`), Tailscale, or a TLS reverse proxy with its own authentication, and set `dashboard.public_url` and a bounded `dashboard.trusted_proxies` in Hermes config. See the upstream [web dashboard guide](https://hermes-agent.nousresearch.com/docs/user-guide/features/web-dashboard).

## Security reporting

Please do not open a public issue containing API keys, private transcripts, or exploit payloads that expose others' systems. Contact the repository maintainer privately through GitHub profile channels for sensitive disclosures. This project has no formal security SLA.
